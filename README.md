# Рули

Приложение для управления иерархией задач команды: ответственные и участники, сроки, результаты и проверка руководителем, обсуждения и график работы. Реализация: React Server Components, Vinext, Cloudflare Workers, D1 и Drizzle. Статические макеты в `designs/` сохранены отдельно; рабочее приложение находится в `app/`.

## Возможности

- Задачи и группы с описанием, сроком, ответственным и участниками. Основные поля доступны сразу; участников и оформление можно раскрыть при необходимости. После создания открывается новая задача.
- Цветные карточки разного размера по умолчанию, компактный список по переключателю и отдельный режим изменения структуры. Сводка «Ждут проверки», «Просрочены», «Срок сегодня» ведёт к конкретным задачам без повторного подсчёта их групп. Поиск и сворачиваемые фильтры по ответственному, статусу и сроку работают вместе.
- Результат можно отправить на проверку вручную или подготовить через API AI-исполнителя. Руководитель принимает его или возвращает в работу.
- Изменения проверяют версию записи. Устаревшая форма не перезаписывает чужие правки; ошибки текста и даты возвращаются без скрытого обрезания введённых значений.
- Удалённая ветка попадает в корзину и восстанавливается целиком. Если родитель удалён, сначала нужно восстановить его. Разбиение поручения можно отменить, пока это не приведёт к потере новых подзадач, отдельного обсуждения или плана.
- Общий чат задачи и отдельные диалоги с участниками; график по дням с учётом загрузки ответственных. При прокрутке обсуждения видны название задачи и выбранный канал.

## Локальный запуск

Команды выполняются из корня репозитория. В `package.json` заявлен Node.js `>=22.13.0`; текущий полный набор проверок запускается на Node.js 24 и использует `node:sqlite` и прямой импорт TypeScript. Для разработки и запуска всех тестов используйте Node.js 24. Установка зависимостей работает в Windows, macOS и Linux.

1. Установите зависимости из lockfile:

   ```sh
   npm run install:ci
   ```

2. Создайте локальный файл `.dev.vars` в корне. **Только для локального тестового входа** его содержимое:

   ```dotenv
   RULI_OWNER_EMAIL=seedy@sites.test
   ```

   `.dev.vars*` исключён из Git. Не помещайте реальные адреса владельца или другие значения окружения в исходники, README, архив публикации или коммиты.

3. Соберите приложение, чтобы получить конфигурацию Worker, затем примените миграции к новой локальной базе:

   ```sh
   npm run build
   node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_striped_tarot.sql
   node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0001_clear_ultragirl.sql
   node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0002_lush_hardball.sql
   node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0003_nosy_pretty_boy.sql
   node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0004_agent_webhooks.sql
   node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0005_bot_request_hash.sql
   ```

   Для существующей базы применяйте только ещё не применённые миграции в порядке номеров. Эти команды `d1 execute` сами не ведут журнал применённых файлов; повторный запуск уже применённого DDL может завершиться ошибкой.

4. Запустите приложение:

   ```sh
   npm run dev
   ```

   Используйте адрес из вывода Vinext; обычно это [http://127.0.0.1:5173](http://127.0.0.1:5173). При необходимости задайте порт: `npm run dev -- --port 5173`.

5. Откройте [локальный вход](http://127.0.0.1:5173/signin-with-chatgpt?return_to=/). В portable-профиле на loopback он создаёт тестовую identity `local_seedy`, email `seedy@sites.test`, имя `Seedy`. При указанном выше локальном `RULI_OWNER_EMAIL` это руководитель. Выход: `/signout-with-chatgpt?return_to=/`.

Локальный mock-вход действует только на сервере разработки и loopback-запросах; в managed-linux он отключён, в производственную сборку не включается. Это способ проверить приложение локально, а не способ авторизации реальной команды.

## База данных и миграции

`.openai/hosting.json` объявляет D1-привязку `DB`; R2 сейчас не используется. Схема описана в `db/schema.ts`, SQL-миграции — в `drizzle/`.

**Схема создаётся и обновляется только миграциями. DDL при обработке запросов нет.** `lib/ruli/bootstrap.ts` при отсутствии корневой задачи добавляет демонстрационную команду и задачи одним batch в уже существующие таблицы. Это не заменяет миграции: без них приложение не запустится.

После изменения схемы:

```sh
npm run db:generate
```

Проверьте созданный SQL и примените только новую миграцию. Для локальной базы используйте команды из раздела запуска с её именем. Рабочие данные dev-сервера и локального Worker хранятся в `.wrangler/state`; указывайте именно этот каталог, без ручного добавления `/v3`.

Локальные миграции с `--local` не изменяют опубликованную базу. При публикации через Sites используйте его процесс сборки и применения миграций. Если развертывание выполняется самостоятельно, примените миграции к целевой D1 перед запуском новой версии приложения.

## Владелец, вход и роли

Для первоначального доступа руководителя обязательна Worker-переменная **`RULI_OWNER_EMAIL`**. В размещённом приложении установите в окружении Worker реальный email владельца, подтверждаемый при входе через ChatGPT. Тестовый `seedy@sites.test` используйте только в локальном окружении разработки.

Первый произвольный посетитель не становится владельцем. При входе с настроенной почтой приложение связывает подтверждённую identity с участником `me` и ролью `manager`. Без настроенного владельца и без предварительно допущенных аккаунтов доступ закрыт. Изменение переменной не удаляет уже созданные привязки аккаунтов.

Размещённая версия использует маршруты авторизации платформы Sites: `/signin-with-chatgpt`, `/signout-with-chatgpt` и `/callback`. Приложение дополнительно проверяет членство в команде через `team_accounts`; одной успешной авторизации недостаточно. Доступ к самому Site и доступ к команде — отдельные проверки.

| Роль | Доступ |
| --- | --- |
| Руководитель (`manager`) | Создание и правка задач, назначения, перестановка, разбиение, корзина, приёмка результатов, управление доступом, чат и график. |
| Исполнитель (`executor`) | Просмотр задач, сдача результата поручений, где он ответственный или явный участник, общий чат и собственные диалоги с руководителем. |
| Наблюдатель (`viewer`) | Просмотр задач, графика и общего обсуждения; без изменений, отправки сообщений и доступа к чужим личным диалогам. |

В разделе «Команда» руководитель добавляет email, имя и роль `executor` или `viewer`. Можно создать нового участника либо связать доступ с существующим человеком команды. Одного исполнителя нельзя привязать к нескольким аккаунтам; бот и участник `me` не подходят для такой привязки.

Добавление доступа не отправляет письмо-приглашение. Передайте участнику ссылку на Site отдельно и разрешите ему доступ к Site, если он закрытый. При первом входе с указанным подтверждённым email запись связывается со стабильным `userId`; дальнейшая проверка использует эту привязку. Состояние первого входа видно руководителю в списке доступов.

## Обсуждения и график

Обсуждение относится к конкретной задаче или группе. Общий канал виден допущенным участникам; писать могут руководитель и исполнители. Отдельный канал с исполнителем доступен руководителю и соответствующему исполнителю. Автор сообщения определяется сервером из identity. Повторная отправка того же сообщения защищена от дублирования. Сначала загружаются последние 100 сообщений; кнопка «Загрузить раньше» открывает предыдущую историю, не теряя уже загруженную переписку.

Диалоги разделены на общий чат, команду и AI; на телефоне список сворачивается. В ленте есть разделители дат, поиск по загруженным сообщениям, копирование, текстовое цитирование, безопасные ссылки, списки и блоки кода. При чтении старой переписки новые сообщения не сбивают прокрутку. Состояние AI и возможность повтора после ошибки приходят с сервера; наличие ключа не выдаётся за статус «онлайн».

На компьютере Enter отправляет сообщение, Shift+Enter добавляет строку; на сенсорном устройстве Enter добавляет строку, а Ctrl/Cmd+Enter отправляет. Черновики хранятся отдельно для каждого пользователя, задачи и канала. Пока AI отвечает, можно редактировать следующий черновик: подтверждение предыдущего сообщения его не удалит. Отправка следующего сообщения доступна после завершения текущего запроса. Ответы AI появляются целиком, без потоковой передачи.

Если отправка отклонена после изменения черновика, исходный текст сохраняется отдельно в блоке «Неотправленные сообщения». Его можно скопировать или добавить к текущему черновику без перезаписи. После длительного отсутствия кнопка истории также загружает пропуски между уже открытой перепиской и последними сообщениями.

Черновики сохраняются в текущей вкладке браузера отдельно для аккаунта, задачи и канала. Изменение графика, обновление страницы и переключение диалогов не очищают набранный текст. После подтверждения успешной отправки очищается только отправленный черновик.

Руководитель формирует график для незавершённых задач внутри выбранной группы: задаёт начало, часы рабочего дня, оценку трудоёмкости задачи и учёт выходных. Генератор распределяет часы по ответственным, учитывает существующую загрузку и сообщает, если результат выходит за сроки или ограничения. Даты и часы записей можно редактировать; превышение дневной загрузки проверяется сервером. Это планирование по заданной оценке, а не автоматический учёт фактически отработанного времени.

Повторная генерация заменяет текущий график и ручные правки только после подтверждения. Поручения, уже включённые в другой план, повторно не планируются. Разбиение переносит существующие записи на исходную подзадачу; безопасная отмена возвращает их обратно. Удаление задачи скрывает связанные обсуждения и графики, восстановление возвращает их.

При смене ответственного график переносится вместе с задачей после проверки загрузки нового исполнителя. Восстановление из корзины и возврат выполненной задачи в работу также проверяют конфликты: при перегрузке операция отклоняется с объяснением. Завершённые задачи сохраняются в истории графика, но не резервируют время для нового планирования. Ручной перенос этапа за срок задачи или её родителя сопровождается предупреждением.

## AI-исполнители

В разделе «Команда» руководитель выбирает для каждого бота провайдера (xAI / Grok, OpenAI или внешний «Grok Bot (агент)»), идентификатор модели или slug агента и рабочие инструкции. Можно настроить существующих ботов или добавить новых. Изменения конфигурации проверяют версию записи. Подключение внешних агентов описано в разделе «Подключение Grok-ботов».

Помощник подключения ведёт по трём шагам: получить ключ у провайдера, добавить серверный секрет в Sites, проверить выбранную модель. Кнопка копирования копирует только имя переменной окружения. Проверка подключения доступна только руководителю и отправляет короткий фиксированный запрос без задач и переписки; она может расходовать API-кредиты. Успех отображается для проверенных провайдера и модели, отдельно от признака наличия ключа. Изменение модели сбрасывает показанный результат проверки.

Ключи хранятся только в серверном окружении: `XAI_API_KEY`, `OPENAI_API_KEY`. Для локальной разработки добавьте нужные значения в исключённый из Git `.dev.vars`; для размещённой версии задайте секреты в Sites и опубликуйте новую версию. `.env.example` содержит только имена переменных. Значения ключей не возвращаются в браузер, сообщения и журнал запусков. Наличие ключа означает готовность конфигурации; валидность ключа и доступ к модели проверяются фактическим запросом к провайдеру.

Для xAI · Grok ключ задаётся как `XAI_API_KEY`. Идентификатор модели выбирается в настройках каждого бота, а не переменной окружения; значение по умолчанию — `grok-4.7` (флагманская модель xAI на ноябрь 2026). Запросы идут на `https://api.x.ai/v1/responses` (Responses API, по форме совместимый с OpenAI Responses), без стриминга и без автоматических повторов, с параметром `store: false`, чтобы переписка не сохранялась на стороне xAI. Ожидание ответа ограничено 45 секундами; для моделей с длинным рассуждением этого может не хватить. Ошибки 401/403, 429 и 5xx показываются безопасным текстом, без тела ответа провайдера.

В личном диалоге с ботом ответ запрашивается при отправке сообщения. В общем чате выберите AI-участника перед отправкой; без выбора сообщение сохраняется как обычное обсуждение. Провайдер получает описание выбранной задачи и ограниченную историю только выбранного канала. Личные диалоги других исполнителей в контекст не попадают. Личные каналы ботов доступны руководителю; исполнители могут запускать AI в общем чате и поручениях, где являются ответственными или участниками. Наблюдатели не запускают AI.

В поручении, назначенном боту, кнопка запуска получает текстовый результат и отправляет его на проверку. AI не принимает результат самостоятельно и не выполняет внешние действия. Если во время запроса изменили задачу или исполнителя, ответ сохраняется в истории и не перезаписывает правки человека.

Запуски сохраняются в `ai_runs`: состояние, модель, ответ, безопасная ошибка и расход токенов, если его вернул провайдер. Дублирующий запрос не создаёт второй ответ; повтор после ошибки выполняется явно. Запросы ограничены по времени и размеру ответа. Тесты используют изолированную SQLite и подменённый HTTP-транспорт; проверка настоящего ответа требует настроенного API-ключа и доступа к выбранной модели.


## Подключение Grok-ботов

Агенты «Grok Bot (агент)» — это внешние боты Владислава (Pinterest, ВКонтакте, Дзен и другие). Они не вызывают модель внутри Рули. Схема: Рули ставит задачу или пишет в чат → исходящий вебхук → бот-диспетчер «Рулю — Дашборд» → нужный агент → ответ обратно через HTTP API Рули.

В разделе «Команда» создайте бота, выберите провайдера «Grok Bot (агент)» и задайте уникальный slug (`vk`, `dzen`, `pinterest` и т.д.). Бота можно назначить ответственным или участником задачи и упомянуть в чате (`@Имя` или `@slug`). Существующие боты xAI и OpenAI не меняются.

### Секреты

Задаются в исключённом из Git `.dev.vars` локально или в секретах Sites / Worker на размещённом сайте. Значения в исходники не помещают.

| Переменная | Назначение |
| --- | --- |
| `GROK_BOT_WEBHOOK_URL` | URL вебхука диспетчера. Если не задан, события не отправляются, в «Команде» показано «Вебхук не настроен». |
| `GROK_BOT_WEBHOOK_KEY` | Ключ отправителя. По умолчанию уходит как `Authorization: Bearer <ключ>`. |
| `GROK_BOT_WEBHOOK_HEADER` | Необязательное имя заголовка. Если задано и это не `Authorization`, ключ кладётся в этот заголовок как есть. |
| `RULI_BOT_API_TOKEN` | Bearer-токен входящего API ботов. Сравнивается в постоянном времени. Без токена все маршруты `/api/bot/*` отвечают 401; вход через ChatGPT для них не требуется. |
| `RULI_BASE_URL` | Публичный адрес приложения без завершающего `/`, например `https://ruli.example`. Используется в `task.url` и `app.baseUrl`. |

Точный способ, которым Grok Bot передаёт «ключ отправителя» в URL вебхука, зависит от приложения; при несовпадении задайте `GROK_BOT_WEBHOOK_HEADER`.

### Исходящие события

Рули ставит событие в таблицу outbox и доставляет его через `fetch` (таймаут 10 с, совместимо с Cloudflare Workers и `waitUntil`). Ошибка доставки не откатывает сохранение задачи или сообщения. На карточке задачи руководитель видит «Передано боту» / «Не доставлено боту» и может нажать «Повторить». Сообщения, написанные самим агентом, этому агенту повторно не отправляются.

События:

- `task.assigned` — бота назначили ответственным или участником;
- `task.updated` — у уже назначенной задачи изменились срок, приоритет или описание (если бот только что назначен, уходит только `task.assigned`);
- `message.created` — новое сообщение в чате задачи, где бот участвует;
- `bot.mentioned` — бота упомянули (`@Имя`), вместо `message.created`.

Пример тела:

```json
{
  "event": "task.assigned",
  "eventId": "9b2c1a0e-1111-2222-3333-444455556666",
  "occurredAt": "2026-11-18T01:00:00.000Z",
  "app": { "baseUrl": "https://ruli.example" },
  "task": {
    "id": "task-1",
    "title": "Оформить пост",
    "description": "Текст",
    "status": "todo",
    "priority": "high",
    "due": "2026-11-20",
    "url": "https://ruli.example/t/task-1",
    "parentId": "group"
  },
  "bot": { "slug": "vk", "name": "ВКонтакте" },
  "participants": [{ "name": "ВКонтакте", "kind": "bot" }]
}
```

Для сообщений добавляется `message`: `{ "id", "author": { "name", "kind": "human"|"bot" }, "text" }`. Диспетчер дедуплицирует события по `eventId`. Личное сообщение получает только адресат этого канала: упоминание другого агента не пересылает ему приватный текст. Личный канал группы работает и для агента, назначенного на её подзадачу.

Руководитель видит недоставленные и ожидающие события отдельно от последних успешных доставок, в том числе в группах. Каждую ошибку можно повторить отдельно. Повтор проверяет актуальное назначение агента, его настройки и доступность задачи; снятому с задачи или выключенному агенту прежний текст не отправляется.

### Входящий API

Авторизация: `Authorization: Bearer $RULI_BOT_API_TOKEN`. Действие всегда от имени бота из поля `bot` (query или JSON) и только в задачах, где он ответственный или участник. Чужая задача — 403, отсутствующая — 404. Повторы POST с тем же `Idempotency-Key` возвращают сохранённый ответ, включая конкурентные повторы; другой маршрут или другое содержимое с тем же новым ключом — 409. Изменение и запись ответа выполняются одной транзакцией. Исторические ключи, созданные до миграции `0005`, сохраняют совместимость с прежними повторами. Текст сообщения — до 5000 символов.

Для ответа на полученное событие передавайте его `replyToEventId`. Сервер проверяет задачу и бота события и сохраняет ответ в исходном канале. Для личного события ответ остаётся личным. Неизвестное, чужое или недоступное событие отклоняется; подмена идентификатора не переключает ответ в общий чат. Без `replyToEventId` новое сообщение публикуется в общем чате задачи. Агент подзадачи может ответить на собственное личное событие группы, но это не даёт ему доступ к общему чату группы или чужим подзадачам.

Статусы как у исполнителя: `todo` ↔ `doing`, из них — в `review`, из `review` обратно в `doing` или в `done`. Для `review` и `done` нужен непустой результат; прямой переход `todo` → `done` запрещён. Уже принятый результат в `done` нельзя заменить через API: сначала руководитель возвращает задачу в работу.

```sh
# Список задач бота
curl -sS -H "Authorization: Bearer $RULI_BOT_API_TOKEN" \
  "$RULI_BASE_URL/api/bot/tasks?bot=vk&status=todo"

# Задача с последними сообщениями
curl -sS -H "Authorization: Bearer $RULI_BOT_API_TOKEN" \
  "$RULI_BASE_URL/api/bot/tasks/task-1?bot=vk"

# Ответ в чат
curl -sS -X POST -H "Authorization: Bearer $RULI_BOT_API_TOKEN" \
  -H "Content-Type: application/json" -H "Idempotency-Key: $(uuidgen)" \
  -d '{"bot":"vk","text":"Пост опубликован.","replyToEventId":"9b2c1a0e-1111-2222-3333-444455556666"}' \
  "$RULI_BASE_URL/api/bot/tasks/task-1/messages"

# Смена статуса (через «На проверке», затем «Готово»)
curl -sS -X POST -H "Authorization: Bearer $RULI_BOT_API_TOKEN" \
  -H "Content-Type: application/json" -H "Idempotency-Key: $(uuidgen)" \
  -d '{"bot":"vk","status":"review","result":"Ссылка на пост"}' \
  "$RULI_BASE_URL/api/bot/tasks/task-1/status"
```

## Команды и проверки

| Команда | Назначение |
| --- | --- |
| `npm run install:ci` | Установка зависимостей из `package-lock.json` с dev/optional-пакетами. |
| `npm run dev` | Приложение Vinext с HMR, обычно порт 5173. |
| `npm run build` | Сборка приложения и Worker в `dist/`. |
| `npm start` | Локальный запуск собранного Worker через `scripts/start-worker.mjs`, `127.0.0.1:8787`. |
| `npm start -- --port 8790` | Тот же Worker на заданном порту. |
| `npm test` | Модель, сроки, планирование, серверные действия и совместная работа, включая SQLite-проверки SQL, ролей и конфликтов версий. |
| `npm run lint` | ESLint. |
| `npx tsc --noEmit` | Проверка TypeScript. |
| `npm run db:generate` | Генерация SQL-миграций после изменения схемы. |
| `npm run dev:designs` | Старые статические макеты на `127.0.0.1:5184`. |
| `npm run build:designs` | Копирование статических макетов в `dist/`. |
| `npm run preview:designs` | Статическое превью содержимого `dist/` на порту 5184. |

`npm start` требует предварительной сборки и миграций, не публикует приложение и не предоставляет mock-вход разработки. Для локальной проверки сценариев с авторизацией используйте `npm run dev`. `build:designs` и сборка приложения используют один каталог `dist/`; перед запуском Worker после работы с макетами снова выполните `npm run build`.

Тесты действий выполняют настоящий SQL в изолированной SQLite-базе, заменяя границы хостинга: D1-транспорт, identity и redirects. Они не заменяют проверку опубликованного Worker с реальными аккаунтами и привязками.

## Структура

- `app/` — страницы задач, команды и корзины; серверные действия и API сообщений.
- `components/ruli/` — интерфейс, формы, обсуждения и график.
- `lib/ruli/model.ts`, `scheduling.ts` — чистая модель и алгоритм распределения работы.
- `lib/ruli/access.ts`, `policy.ts` — членство в команде и права.
- `lib/ruli/data.ts`, `bootstrap.ts`, `mutations.ts`, `collaboration.ts` — чтение, начальные данные и изменения D1.
- `db/schema.ts`, `drizzle/` — схема и миграции.
- `worker/index.ts`, `vite.config.ts`, `.openai/hosting.json` — Worker, локальные привязки и размещение Sites.
- `tests/` — модельные и интеграционные проверки.
- `designs/` — прежние автономные макеты, не использующие текущую D1.

Локальные `.dev.vars*`, `.env*`, `.wrangler/`, `.vinext/`, `.sites-runtime/`, `outputs/` и зависимости исключены из Git. При работе через Sites следуйте инструкции его плагина для выбранного portable/managed-linux окружения, сборки и публикации. Не включайте локальные данные D1 или файлы окружения в архив исходников.
